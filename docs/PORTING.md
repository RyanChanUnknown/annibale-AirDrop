# 移植记录与建议

本文记录 K90 当前实测方案的难点、证据和取舍。适用范围是 README 中锁定的硬件及系统组合，不构成其他机型已经可用的承诺。

## 先分清链路，再改代码

完整链路是原生小米互传会话 → XosBridge → 无线切换和 Wonder → xos0 → mDNS 发现 → 文件传输。界面显示“搜索中”只能证明前端进入状态；看到网卡也不能证明查询已经发出。分别记录 Binder 调用、监督进程退出码、驱动与接口状态、收发包和最终文件哈希，比同时修改多层更容易找出原因。

### Binder 调用失败，恢复成功却掩盖了错误

早期监督进程在报告就绪前退出，返回码是 2；恢复路径返回 0，容易被误判为启动成功。实际问题涉及 Binder `shellCommand` 传递 stdout/stderr：直接打开的 `/data/adb` 日志文件带有服务不能接收的 SELinux 标签。

处理方式是把监督进程的 stdout 和 stderr **都**接到管道，由单独的 logger 打开日志文件，并分别保存启动结果与恢复结果。保持 SELinux Enforcing，不用放宽全局策略掩盖文件描述符问题。

### flock 不是“加一行就结束”

启动脚本锁住文件后，后台进程可能继承同一个描述符，导致调用者退出后仍占锁。修复时既要保证传入 busybox flock 的描述符存在，也要在脱离父进程的子进程中关闭控制锁描述符。停止测试要等监督进程退出、锁可再次获取，不能只看到 `STOCK_RESTORED` 就立即重启。

### 同一芯片不等于同一个可加载模块

SoC、PCI ID、内核版本字符串只能缩小范围。还必须核对配置、符号 CRC、KCFI 类型、模块入口重定位，以及实机原厂 WLAN 的身份。当前安装器同时锁定完整 `/proc/version` 哈希和驱动、固件、已载入驱动 build-id；避免只用可能被 SUSFS 修改的 `uname -r`。

早期国家码问题和后续 Binder/UID 查询失败属于不同故障阶段。旧日志只能提供线索，不能替代当前首个失败命令。最终方案保留实机国家码与频宽校验。

### 页面生命周期无法覆盖所有分享入口

只监听“与 Apple 设备互传”的设置页面，会漏掉文件管理和相册的发送会话；手动开关再叠加页面强制启停，又会形成多个控制者争抢后端。

最终让原生会话的 begin/release 和客户端死亡决定无线生命周期。空闲桥接驻留，普通 Wi-Fi 正常；发送/接收期间独占无线，会话释放后经过宽限期恢复。LSPosed 只在独占期间处理原生互传对 Wi-Fi 关闭的判断。磁贴只负责导航，不再持有持续待收状态。

### root 能打开的页面，普通 APK 未必能打开

接收 Activity 没有对第三方导出，`su am start` 成功不能证明磁贴也能使用。最终通过原 APK 已导出的分享 trampoline 进入，仅对本模块显式标记的请求改变原生跳转目标，保留原生引导和授权流程。普通分享请求不变，兼容 APK 无需单独 root，也不修改或重新签名小米互传。

### 重复搜索失败，根因收敛到 mDNS 出站网卡

现象是第一次能发现 iPhone，退出后再进找不到；切换 iPhone 的隔空投送又恢复。这个关联不足以证明是蓝牙广播缓存。

抓包曾在 20 秒窗口看到 xos0 接收 18 包、发送 0 包。显式指定 xos0 发查询后可见发送，最终在小米互传进程对加入 `ff02::fb:5353`、本地端口 5353、网卡 xos0 的 `MulticastSocket` 设置出站网卡，并设置 hop limit 255。加入组播和选择出站网卡是两个动作。

修复后连续三次重新进入分享均发现目标，文件与图片入口通过，用户又确认文件管理及相册重复搜索正常。网卡绑定是本次证据收敛的关键；没有单独对 hop limit 做因果隔离实验。期间尝试的 BLE payload、nonce 和随机地址变体没有解决问题，已全部移除，最终保留原生蓝牙行为。

### 可用内存不代表高阶连续分配一定成功

一次 Wonder order-5 分配失败发生在仍有约 3 GB 可用内存时。回滚恢复成功，重启后后续测试通过；这不能证明已经修复内存泄漏，也不能仅凭总空闲量排除碎片。建议增加长时间及内存压力下的重复加载测试，保留失败即恢复，避免无限重试或默认清缓存。

### 安装和开机保护都要测试失败分支

只在刷入时检查，挡不住后续 OTA。当前早期检查设备、系统与完整内核身份，开机完成后再检查依赖和文件；失败创建 disable 标记并阻止后端。批准记录绑定本次 boot_id 和文件清单摘要。

新鲜开机时 `sys.xos.exclusive` 可能尚未设置，不能把空值错误地视作无线被占用；只接受空值或 0，其他状态仍拒绝。持久清单不包括安装器结束后会被管理器移除的安装专用文件。此机制用于兼容性保护，不是对拥有 root 的攻击者提供不可绕过的完整性证明。

### Windows 交接也会引入故障

对已存在目录使用 `adb push` 时要注意嵌套层级；shell 脚本统一 LF。签名私钥独立保管，不提交仓库；不同签名的同包名 APK 不能直接覆盖，也不应为了安装成功就自动卸载用户应用。

## 后续建议与判断

先把恢复路径做可靠，再扩展功能。每个新机型应建立独立硬件、系统、内核、原厂文件和依赖矩阵；不能靠删掉版本判断“兼容”新 ROM。分开标明“源码已提供”“可重新打包”“已从源码重编”“新产物已实机验证”。

蓝牙可以低功耗提示附近发送活动，但不代表 Wi-Fi 后端关闭时就能作为完整 AirDrop 目标被发现。本项目曾尝试通知确认唤醒，未达到预期且已取消。普通 Wi-Fi 与当前 AWDL 后端共存需要进一步研究驱动与固件，不能靠一个后台服务开关承诺实现。

建议优先补齐以下验证；这些是计划，并非已经完成的成绩：

1. 20–50 轮双入口重复发现，记录失败率和发现耗时 P95。
2. 大文件传输、取消、进程死亡、锁屏及恢复的组合测试。
3. 内存碎片压力下重复加载，以及失败后的原厂无线恢复。
4. 实测待机与传输功耗，再讨论续航；不能把观察到的低 CPU 等同于零耗电。
5. 每个 OTA 先重新验证 ABI 和恢复，再建立新版本允许矩阵。

固件分发与代码许可分开处理：公共包只含运行代码和固定哈希，外部固件由用户获取、安装时导入；不要把其他项目的分发许可当作自己的授权。详见 [固件授权说明](FIRMWARE-LICENSING.md)。
